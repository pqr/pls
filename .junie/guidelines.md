# Инструкции проекта

## Где искать правила

- Для архитектуры Light используй `src/Light/Docs/_All.md` как указатель. Открывай тематический документ по задаче: диалоги (открытие, submit, кастомизация) — `Dialog.md`; валидация объекта и табличных частей — `Validation.md`; объект/поля/табличные части — `Obj.md`, `Field.md`, `Subtable.md`; наследование Basis/BasisCore/Light — `Namespaces.md`; миграции — `Migration.md`; Email — `Email-Mailer.md` и `EmailTemplate.md`; отладка — `Debug.md`; тестирование — `Testing.md`. Все документы Light находятся в `src/Light/Docs/`, если не указан другой путь.
- При рефакторинге или выборе формы новой логики сверяй подробные примеры с `src/Light/Docs/CodeSimplicity.md`.
- Несовместимое изменение общего слоя (`src`, `src/Light`, `src/BasisCore`, `src/ZeroVat`, `src_LightV2`: удалён/переименован публичный API, css-класс, ключ; нужны ручные шаги в других проектах) сопровождай upgrade-пакетом `<слой>/upgrade/ДАТА_slug/` по `src/Light/Docs/Upgrade.md` (создание — `light-sync.sh upgrades new`; для PHP-рефакторинга готовь `rector.php`; маркер `BREAKING:` в коммит `light-sync` поставит сам, при ручном коммите слоя начни сообщение с него). Пакет — это инструкция и скрипты (`check.sh`, `apply.*`, Rector), которые вместе с кодом слоя приходят в другие проекты через hg. После `light-sync` смотри открытые пакеты (`light-sync.sh upgrades`); состояние проекта — `upgrade/applied.json` в корне.
- При создании и обновлении документации модуля используй skill `light-docs` и `src/Light/Docs/AppDocsRules.md`. Индекс модулей — генерируемый `docs/INDEX.md`.
- Изменение, которое пользователь видит или может потрогать (новая кнопка, массовое действие, поле, отчёт, заметное изменение поведения), записывай в `UserManual/<Модуль>Changelog.html` модуля: секция с датой, изменения одного дня — в одной секции, `basis-doc-updated` — `ГГГГ-ММ-ДД ЧЧ:ММ` строго позже прежнего. Рефакторинги и мелкие багфиксы не пишутся. Правила — skill `light-docs`, раздел «Changelog модуля» в `AppDocsRules.md`.
- При изучении, проверке и отладке кода проверь доступность MCP PhpStorm: поиск символов, инспекции, запуск тестов и Xdebug описаны в `src/Light/Docs/Debug.md` и `src/Light/Docs/Testing.md`.

## Работа с файлами

- Сохраняй чужие и неожиданные изменения, включая неотслеживаемые файлы; не откатывай их.
- Дампы, HTML/SQL-выгрузки и другие временные файлы размещай только в `temp/` корня проекта.
- Общие слои `src/` (предметные неймспейсы), `src/Light`, `src/BasisCore`, `src/ZeroVat`, `src_LightV2` — вложенные hg-репозитории, общие для всех проектов; проектный слой — только `src/Basis`. Синхронизацию слоёв (commit, pull/merge, миграции, push) выполняй skill `light-sync`; схема слоёв — `src/Light/Docs/Namespaces.md`.
- Не исследуй и не редактируй результаты сборки: `src/Light/public/js/build/lightbuild.js` и всё в `src/Light/public/css/`. Исходники движка: `src/Light/TypeScript/` и css в `src/Light/CssSource/<дизайн>/`. Долгоживущие `make light` и `make css` запускай в фоне.

## Код и проектные инварианты

- PHP 8.4. Используй ранний `return`, позитивные предикаты (`shouldX()` означает «делать X»), значение по умолчанию перед условием вместо `else`; не используй `empty()` и короткий тернарный `?:`. Для десятичной арифметики используй стандартный PHP, без функций BCMath (`bc*`).
- Комментарии и PHPDoc пиши на русском. Каждую новую регулярку сопровождай комментарием о том, что она ищет или заменяет. Многострочный SQL оформляй через `<<<SQL`.
- В `src/` сообщения о ходе работы выводи через `Msg`, ошибки — через `ErrorHandler::reportException()` / `reportError()`; не используй Laravel `Log`. Подробности: `src/Light/Docs/ErrorHandler.md`.
- Экранируй вывод через `e()`. Суммы форматируй через `FieldMoney::beautify()` / `FieldMoneyWithCurrency::beautify()`. Значение поля MoneyWithCurrency в `ObjAbstract` включает валюту и сумму одной строкой; разделяй через `FieldMoneyWithCurrency::getAsTuple()`.
- Для пользовательских сообщений получай название модуля через `ModuleRegister::getModuleName(класс модуля)`, предпочитай номер документа или `Name` внутреннему ID; при доступной HTML-ссылке на запись используй `Link::create(...)->view($id)->blank()`. В `$dbLogMsg` не используй `->blank()`.
- Создавай переопределяемые объекты модулей через `ModuleRegister::createModuleObj(класс модуля)`, не через `new SomeObj()` или `SomeObj::find($id)`. Для загрузки по ID используй `SomeObj::createModuleObjAndFind($id)`; см. `src/Light/Docs/Obj.md`.
- Каждое самостоятельное действие в `afterSubmit()` помещай в отдельный `private`-метод с `try/catch`; в `catch` вызывай `ErrorHandler::reportException($e)`. Так ошибка одного действия не прерывает остальные.
- Сервис расчёта снабжай русским PHPDoc с бизнес-целью и алгоритмом; если сервис содержит несколько алгоритмов, документируй методы. Для нетипового сервиса укажи момент вызова, развилки и побочные эффекты (БД, файлы, API, dblog, отчёт).
- Уникально настроенное поле из `initAdditionalListFields()` описывай в `Fields/<Модуль>ListFields.php`.
- Поле, добавленное в объект, автоматически доступно в списке и выгрузке Excel; не уточняй это у пользователя при обычном добавлении поля. Детали: `src/Light/Docs/Field.md`.
- CSS-классы оформляй в BEM с PascalCase: `Block-Element__Modifier`. Для ajax-запросов используй jQuery `$.ajax(...)`.
- Для клиентской логики модуля используй `src/Basis/Module/<Module>/<Module>{Edit,List,View}.ts` и `namespace <Module>Edit { declare var Light: any; … }`; обращайся к API через глобальный `Light`. `ModuleAbstract::initCssJs()` автоматически подключает соответствующие скомпилированные JS/CSS. Компиляция — `make js` (`tsc`); см. `src/Light/Docs/Module.md`.
- Если текст textarea/CKEditor отправляется ajax-запросом в ИИ, показывай состояние AiInput: `'aiInput' => true` для диалога, `Light.ai.setBusy($el, bool)` в TS или `data-ai-input-target` для htmx; см. `src/Light/Docs/AiInput.md`.

## Упрощение кода

- Возвращай нужные значения напрямую без промежуточных обёрток. Передавай конкретное значение или enum вместо флага, из которого его затем вычисляют.
- Читай параметры запроса в action/контроллере и передавай в бизнес-логику явно. Для составных ключей выбирай разделитель, которого нет в данных (`|` вместо неоднозначного `_`).
- Не добавляй методы для простого `match` и методы-прокси. Размещай создание ссылки на Action в самом классе Action.
- Используй конкретные типы вместо nullable с вычислением дефолта внутри метода. Упрощай проверки конкретного варианта и не рассчитывай неиспользуемые значения.
- Для получения одной колонки используй `Db::getCol()`; когда достаточно, объединяй результаты через `array_merge()` и `array_unique()` без ручных циклов.
- Подробные примеры всех правил: `src/Light/Docs/CodeSimplicity.md`.
- Если видишь потенциальную гонку записи или чтения - не делай сразу LOCK, переспроси пользователя на сколько данная ситуация частая и требуется ли безопасная обработка гонки (цель: не переусложноить код лишними LOCK). 

## База данных

- Текущая БД проекта: `pls_dev`. Структуры таблиц находятся в `database/tables_sql_structure/*.sql`. Для локального mysql используй уже настроенный доступ из `.my.cnf`, не передавай пароль в командной строке.
- Денежные суммы храни как `DECIMAL(17, 2)`; POL, POD, Location и прочие UNLOCODE-ссылки — как `VARCHAR(10)` с FK на `location.UNLOCODE ON UPDATE CASCADE`.
- Миграции делай по `src/Light/Docs/Migration.md`, с текущей датой в имени. Новую локальную миграцию применяй к `pls_dev` через mysql и проверяй затронутый интерфейс через curl.
- После изменения структуры таблицы обнови её файл в `database/tables_sql_structure/` через `./mysqldump_tables_sql_structure.sh <table_name>`.

## Проверки изменений

- PHP: для изменённых файлов запусти `env XDEBUG_MODE=off vendor/bin/phpstan analyse --memory-limit=-1 -c phpstan-unlimited.neon <изменённые.php>` и исправь ошибки.
- `src/Basis/Module/<Модуль>/**`: запусти `env XDEBUG_MODE=off vendor/bin/codecept run Functional <Модуль>Cest`; сообщение `File or path ... not found` означает, что тестов модуля нет.
- TypeScript: выполни `tsc`. Для сложной чистой публичной логики напиши PHPUnit-тест (`src/Light/Tests/` для кода `src/Light/`, иначе `tests/Unit/`). Не используй `RefreshDatabase`.
- Изменения веб-интерфейса проверяй через `curl` к `http://pls.test` с `auth_user=<логин>` и `debug_footer=1`; для списка добавь `debug_table_load_sync=1`. Проверь нужный результат и отсутствие `fatal`, `SqlQueryError`, `ErrorUnknownField`, `<!-- ERROR:`. Полная процедура: `src/Light/Docs/Testing.md` и `Debug.md`.
- На локальной dev-базе после тестирования не откатывай данные: настройки пользователей (`user_filter`, `user_filter_history`, `user_tableparam` и другие `user_*`) и разовые тестовые записи остаются как есть. Бэкап перед curl и восстановление после не нужны — не трать на это силы.
- Браузер при обычной проверке не запускай. Для сложного TS/DOM-сценария используй skill `playwright` в headless-режиме; видимое окно — только по прямой просьбе пользователя или если иначе проблему не воспроизвести. Проверяй DOM, значения полей, `console` и `pageerror`, затем выполни применимые `tsc`, PHPStan, Codeception и curl.
- Email проверяй по `queue_email`, телу письма и связям с объектом, а не по факту доставки в тестовой среде; см. `src/Light/Docs/Testing.md` и `Email-Mailer.md`.
